
## 1. 架构目标

  

`AI Relationship Oracle（AI 情感关系顾问）` 的系统架构目标是：

  

1. 支撑用户基础档案与对象基础档案；

2. 支撑首次咨询自动建档与后续持续咨询；

3. 支撑 `Profile（事实档案）` 与 `Memory（AI 关系记忆）` 分层；

4. 支撑用户可选的多分析维度工具链；

5. 支撑关系记忆的自动沉淀、重大事件更新和人工纠偏；

6. 支撑线上咨询系统与离线评测系统并行演进。

  

---

  

## 2. 总体架构

  

### 2.1 线上系统

  

```text

用户

  ↓

Frontend（Vue3 + TypeScript）

  ↓

FastAPI（后端接口服务）

  ↓

LangGraph（工作流编排）

  ↓

LLM Provider（GPT / Claude）

  ↓

返回结果

```

  

### 2.2 LangGraph 内部主流程

  

```text

用户消息

  ↓

Intent Router（意图路由器）

  ↓

Entity Extractor（实体提取器）

  ↓

Profile Loader（档案加载器）

  ↓

Memory Loader（记忆加载器）

  ↓

Tool Router（工具路由器）

  ├─ Bazi Engine（八字分析引擎）

  ├─ Psychology Engine（心理学分析引擎）

  └─ Tarot Engine（塔罗分析引擎，可选）

  ↓

Knowledge RAG（知识检索增强生成）

  ↓

Compatibility Engine（融合分析引擎）

  ↓

Prompt Builder（提示词构建器）

  ↓

LLM Generator（大模型生成器）

  ↓

Persist Result（结果持久化）

```

  

### 2.3 离线评测系统

  

```text

Evaluation Harness

  ↓

测试 Case

  ↓

Agent Workflow

  ↓

GPT / Claude

  ↓

评分器（规则 + LLM Judge + Ragas）

  ↓

评测报告

```

## 3. 分层架构说明

  

### 3.1 Frontend（前端层）

  

负责：

  

- 登录注册；

- 用户本人基础出生信息录入；

- 对象基础信息录入与补充；

- AI 咨询聊天界面；

- 分析维度选择器；

- 报告生成与查看；

- 候选事件确认与关系快照人工修正。

  

重要说明：

  

- 前端不要求用户在每次咨询前手工维护完整关系状态与时间线；

- 关系快照和时间线以系统自动沉淀为主；

- 用户主要负责输入基础事实与必要纠偏。

  

---

  

### 3.2 API Layer（接口层）

  

负责：

  

- 接收前端请求；

- 鉴权；

- 参数校验；

- 调用业务服务；

- 返回统一响应。

  

推荐技术：

  

- `FastAPI`

  

---

  

### 3.3 Service Layer（业务服务层）

  

负责：

  

- 用户服务；

- 档案服务；

- 对象服务；

- 会话服务；

- 记忆服务；

- 报告服务；

- 评测服务；

- 咨询服务。

  

原则：

  

- API 层不直接承载复杂业务逻辑；

- LangGraph 不直接管理所有数据库细节；

- Service 层负责业务数据与 Agent 工作流的衔接。

  

---

  

### 3.4 Agent Layer（AI 工作流层）

  

V1 采用：

  

```text

单 Agent + 多 Tool

```

  

核心组件：

  

- `LangGraph`

- `Intent Router`

- `Entity Extractor`

- `Profile Loader`

- `Memory Loader`

- `Event Detector`

- `Prompt Center`

  

关键职责：

  

1. 判断用户问题类型；

2. 支持无 `partner_id` 的首次咨询；

3. 从用户文本中自动提取对象并创建初始对象档案；

4. 读取事实档案和 AI 关系记忆；

5. 根据用户勾选的分析维度动态调度工具；

6. 在回答后决定是否沉淀关系快照、关系事件和长期记忆。

  

---

  

### 3.5 Tool Layer（工具层）

  

工具层不是直接生成最终回答，而是输出结构化 JSON 结果包。

  

V1 工具：

  

- `Bazi Engine`

- `Psychology Engine`

- `Tarot Engine`

- `RAG Retriever`

- `Compatibility Engine`

  

工具层原则：

  

1. 输出结构化结果，不直接输出面向用户的长文；

2. 核心规则计算尽量不用 LLM；

3. 解释层可由小模型辅助；

4. 支持按用户选择动态启用；

5. 未来可扩展为统一分析维度系统。

  

统一结果示意：

  

```json

{

  "tool": "bazi",

  "core_signals": [],

  "risks": [],

  "opportunities": [],

  "actions": [],

  "confidence_notes": []

}

```

  

---

  

### 3.6 Data Layer（数据层）

  

数据层分两大部分：

  

```text

Profile（事实档案）

+

Memory（AI 关系记忆）

```

  

#### Profile

  

- `user`

- `user_profile`

- `partner_profile`

  

特点：

  

- 用户填写；

- 系统计算基础命盘；

- 不允许模型随意改写。

  

#### Memory

  

- `relationship_profile`

- `relationship_event`

- `relationship_event_candidate`

- `conversation`

- `conversation_message`

- `memory_summary`

- `report`

  

特点：

  

- 来自聊天与分析沉淀；

- 允许 AI 自动更新；

- 允许用户纠偏；

- 是后续咨询最关键的上下文层。

  

技术组件：

  

- `PostgreSQL`：业务数据和长期记忆；

- `Redis`：短期上下文与最近对话；

- `Milvus`：知识库向量，不存用户记忆。

## 4. 关键运行逻辑

  

### 4.1 首次咨询自动建档

  

如果用户第一次进入系统就直接发问，例如：

  

```text

我和 Sarah 分手三个月了，最近她点赞我朋友圈，她会回来吗？

```

  

系统流程：

  

```text

Intent Router

  ↓

Relationship Flow

  ↓

Entity Extractor

  ↓

提取 Sarah

  ↓

自动创建 partner_profile

  ↓

自动创建 relationship_profile

  ↓

自动创建 memory_summary

  ↓

继续分析

```

  

这意味着：

  

- 首次咨询允许无 `partner_id`；

- 用户不需要先补全所有对象资料；

- 后续再补出生日期、出生时间、出生地点即可。

  

---

  

### 4.2 重大事件驱动更新

  

`relationship_profile` 不是每轮聊天都更新。

  

推荐流程：

  

```text

Message

  ↓

Event Detector

  ↓

发现重大变化

  ↓

Update relationship_profile

```

  

重大事件包括：

  

- 开始恋爱

- 分手

- 断联

- 复联

- 结婚

- 离婚

- 目标改变

  

否则：

  

- 仅保存 `conversation_message`

- 不更新 `relationship_profile`

  

---

  

### 4.3 用户选择分析维度

  

用户可在 UI 中选择：

  

- ☑ 八字分析

- ☑ 心理学分析

- ☐ 塔罗分析

  

后端根据 `analysis_methods` 动态调度工具。

  

例如：

  

```json

{

  "analysis_methods": ["bazi", "psychology"]

}

```

  

对应流程：

  

```text

Relationship Flow

  ↓

Bazi Engine

  ↓

Psychology Engine

  ↓

Compatibility Engine

  ↓

GPT

```

  

---

  

### 4.4 报告与聊天分离

  

聊天不自动生成正式报告。

  

正确流程：

  

```text

聊天 → conversation_message

用户主动点击生成报告 → Report Builder → report

```

  

这保证：

  

- 聊天数据库不会被报告泛滥污染；

- 报告成为有明确意图的正式产物。

## 6. 架构结论

  

当前系统的正式架构可以压缩为：

  

```text

线上：用户 → FastAPI → LangGraph → GPT → 返回结果

离线：Harness → Case → Workflow → Judge → Report

数据：Profile + Memory

核心：Intent Router + Compatibility Engine + Memory Builder + Prompt Center

```

  

这套结构既能保证 V1 快速落地，也为后续工具扩展、评测演进和商业化留足空间。
