## 1. 文档目的

  

本文档将 `AI Relationship Oracle` 的整体规划拆解为可执行的研发任务，便于产品、前端、后端、AI、测试协作开发。

  

本文档已经统一到最终版项目架构：

  

- 首次咨询自动建档；

- `Profile + Memory` 数据分层；

- 用户可选分析维度；

- 关系快照重大事件驱动更新；

- 聊天与报告分离；

- V1 同时建设 `Harness + Ragas`。

  

---

  

## 2. 任务拆解原则

  

### 2.1 按闭环拆，不按名词堆拆

  

正确做法：

  

```text

事实档案闭环

首次咨询自动建档闭环

关系记忆闭环

分析维度与工具闭环

报告闭环

评测闭环

```

  

而不是一开始就按：

  

```text

八字

塔罗

心理学

RAG

LangGraph

```

  

分散开发。

  

### 2.2 先做事实档案，再做记忆与分析

  

因为 AI 咨询的前提是：

  

- 知道用户是谁；

- 知道对象是谁；

- 知道命盘基础是什么。

  

### 2.3 先让用户低门槛进入，再做重型功能

  

不能先做一套复杂关系维护系统，再考虑聊天。

  

正确顺序应是：

  

```text

先咨询可用

再记忆沉淀可用

再优化补录体验

```

  

### 2.4 先做可评测链路，再持续迭代

  

Prompt、Router、Memory、RAG、Compatibility 都会频繁改，必须尽早接入评测。

## 7. 当前最关键的实现约束

  

1. 不能退回到“用户手工维护完整关系表单”的旧设计；

2. `relationship_profile` 不能每轮都更新；

3. `memory_summary` 不能按 conversation 维度切碎；

4. 工具不能直接输出最终长文给用户；

5. 聊天不能默认自动生成报告；

6. RAG 不能替代用户记忆层；

7. Prompt 改动必须走 Harness 回归；

8. 用户不会写 Prompt，所有 Prompt 必须由系统固定模板管理。

## 8. 任务拆解结论

  

当前最合理的工程实施顺序是：

  

```text

事实档案

→ 首次自动建档

→ Prompt 基础模板

→ 关系记忆

→ 工具层

→ Compatibility + Prompt Center

→ 报告系统

→ RAG

→ Harness + Ragas

```

  

这份拆解应该作为当前研发分工与排期的直接依据。
