## 1. 设计目标

  

数据模型的核心目标是支撑：

  

1. 用户本人基础档案；

2. 关系对象基础档案；

3. 关系当前快照；

4. 关系历史事件时间轴；

5. 长短期记忆；

6. AI 咨询会话；

7. 用户主动触发的正式报告；

8. 离线评测体系；

9. `Profile（事实档案） + Memory（AI 关系记忆） + Output（正式输出）` 分层结构。

  

本项目的数据设计必须以“某个用户与某个对象之间的长期关系理解”为中心，而不是以单次聊天为中心。

  

---

  

## 2. 数据库选择

  

### 2.1 PostgreSQL

  

用于保存核心业务数据与长期记忆。

  

包括：

  

- 用户；

- 用户档案；

- 对象档案；

- 关系快照；

- 关系事件；

- 候选事件；

- 会话；

- 原始聊天消息；

- 长期记忆摘要；

- 报告；

- 订阅与支付；

- 评测案例与评测结果。

  

### 2.2 Redis

  

用于保存短期上下文。

  

包括：

  

- 最近 10~20 轮聊天；

- 临时工作流状态；

- 短期会话缓存。

  

### 2.3 Milvus

  

用于保存知识库向量。

  

包括：

  

- 命理知识片段；

- 塔罗知识片段；

- 心理学知识片段。

  

注意：Milvus 不存用户隐私记忆和聊天记录。

  

---

  

## 3. 数据分层

  

### 3.1 Profile（事实档案层）

  

特点：

  

- 用户填写；

- 系统计算基础命盘；

- 不允许模型随意改写；

- 是 AI 分析的硬事实输入。

  

包含：

  

- `user`

- `user_profile`

- `partner_profile`

  

### 3.2 Memory（AI 关系记忆层）

  

特点：

  

- 从聊天与分析中自动沉淀；

- 支持 AI 自动更新；

- 支持用户纠偏；

- 是后续咨询最重要的上下文层。

  

包含：

  

- `relationship_profile`

- `relationship_event`

- `relationship_event_candidate`

- `conversation`

- `conversation_message`

- `memory_summary`

  

### 3.3 Output（正式输出层）

  

特点：

  

- 不是长期记忆本体；

- 是用户主动触发生成的正式产物；

- 应与普通聊天分离。

  

包含：

  

- `report`

  

---

  

## 4. 核心数据关系

  

```text

user

 ├─ 1:1 user_profile

 ├─ 1:N partner_profile

 ├─ 1:N conversation

 ├─ 1:N report

 ├─ 1:N subscription

 └─ 1:N payment_order

  

partner_profile

 ├─ 1:1 relationship_profile（按 user_id + partner_id 唯一）

 ├─ 1:N relationship_event

 ├─ 1:N relationship_event_candidate

 ├─ 1:N conversation

 ├─ 1:1 memory_summary（按 user_id + partner_id 唯一）

 └─ 1:N report

  

conversation

 └─ 1:N conversation_message

```

  

说明：

  

- `relationship_profile` 代表“当前快照”，不是多版本流水主表；

- `relationship_event` 代表“历史时间轴”；

- `memory_summary` 代表“这段关系的唯一主长期摘要”；

- `report` 属于正式输出层，不属于长期记忆本体；

- 多个 `conversation` 可以共享同一个 `partner_id` 的长期关系记忆。

## 6. user

  

作用：保存账号主体信息。

  

建议字段：

  

```text

id

email

password_hash

register_time

status

created_at

updated_at

```

  

`status` 建议值：

  

```text

active

disabled

deleted

```

  

---

  

## 7. user_profile

  

作用：保存用户个人命盘档案。

  

建议字段：

  

```text

id

user_id

gender

birth_date

birth_time

birth_city

birth_country

bazi_chart

five_elements

created_at

updated_at

```

  

说明：

  

- 用户只需要先填自己的出生信息即可开始使用；

- `bazi_chart`、`five_elements` 由系统计算；

- 出生时间可为空，后续命理分析需降级处理。

  

---

  

## 8. partner_profile

  

作用：保存关系对象基础档案。

  

建议字段：

  

```text

id

user_id

nickname

gender

relationship_type

birth_date

birth_time

birth_city

birth_country

bazi_chart

created_at

updated_at

```

  

`relationship_type` 建议值：

  

```text

ex

current

crush

spouse

friend

unknown

```

  

说明：

  

- 首次咨询前允许没有 `partner_id`；

- 系统可从用户首轮聊天中提取 `nickname` 自动建档；

- 对象出生信息允许为空，后续逐步补充。

  

---

  

## 9. relationship_profile

  

作用：保存“当前关系快照”，是 Agent 回答优先读取的核心表之一。

  

建议字段：

  

```text

id

user_id

partner_id

current_status

current_goal

relationship_stage

interaction_pattern

trust_level

conflict_level

intimacy_level

last_major_event

summary_snapshot

updated_by

updated_at

created_at

```

  

说明：

  

- 应保证 `user_id + partner_id` 唯一；

- 不应在每轮聊天后都更新；

- 以“重大关系事件”作为更新触发条件；

- `updated_by` 用于标识 AI 自动更新或用户人工修正。

  

`updated_by` 建议值：

  

```text

system

user

```

  

---

  

## 10. relationship_event

  

作用：保存高置信度、已确认的关系事件时间轴。

  

建议字段：

  

```text

id

user_id

partner_id

event_type

event_date

description

source

confidence_score

created_at

```

  

`event_type` 示例：

  

```text

met

started_relationship

breakup

no_contact

reconnect

marriage

divorce

confession

major_conflict

```

  

说明：

  

- 只保存高置信度或用户确认后的事件；

- 是关系历史时间线的正式来源之一；

- 可供报告生成与长期分析使用。

  

---

  

## 11. relationship_event_candidate

  

作用：保存低置信度、待用户确认的候选关系事件。

  

建议字段：

  

```text

id

user_id

partner_id

event_type

event_date

description

source

confidence_score

candidate_status

created_at

confirmed_at

```

  

`candidate_status` 建议值：

  

```text

pending

confirmed

rejected

```

  

说明：

  

- 例如“她最近好像态度变好了”这类信息，不应直接进入正式时间轴；

- 用户确认后可转正写入 `relationship_event`；

- 这是降低模型误写记忆风险的重要缓冲层。

  

---

  

## 12. conversation

  

作用：保存一次咨询会话。

  

建议字段：

  

```text

id

user_id

partner_id

title

conversation_type

created_at

updated_at

```

  

说明：

  

- `partner_id` 允许为空，仅在自动建档完成前短暂存在；

- 自动建档完成后应尽量补回 `partner_id`；

- 多个 conversation 可对应同一对象。

  

`conversation_type` 建议值：

  

```text

relationship_analysis

emotional_support

general_guidance

```

  

---

  

## 13. conversation_message

  

作用：保存原始聊天消息，是审计、追溯、短期上下文重建的重要底层数据。

  

建议字段：

  

```text

id

conversation_id

role

content

message_type

created_at

```

  

`role` 建议值：

  

```text

user

assistant

system

```

  

说明：

  

- 所有对话都应落库；

- 短期上下文虽然优先走 Redis，但 PostgreSQL 中仍保留原始消息；

- 未来评测失败案例回放也会依赖这里。

  

---

  

## 14. memory_summary

  

作用：保存“某个用户与某个对象关系”的唯一长期记忆摘要。

  

建议字段：

  

```text

id

user_id

partner_id

summary

summary_version

updated_at

created_at

```

  

说明：

  

- 必须保证 `user_id + partner_id` 唯一；

- 不是按 `conversation_id` 维护；

- 由 AI 自动更新为主，用户人工修正为辅；

- 是后续咨询中最关键的长期上下文之一。

  

---

建议字段：

  

```text

partner_id

说明：

  

- 不应每次聊天自动生成；

- 仅在用户主动触发时生成；

- 报告与普通聊天消息分层存储。

  

`report_type` 示例：

```

## 22. 设计结论

  

当前数据模型的关键原则已经明确：

  

1. 数据按 `Profile + Memory + Output` 分层；

2. `memory_summary` 按 `user_id + partner_id` 唯一维护；

3. `relationship_profile` 不是每轮都更新；

4. `relationship_event_candidate` 用于承接低置信度事件；

5. `report` 与普通聊天分离；

6. Milvus 只做知识向量检索，不存用户长期记忆。

  

这套设计可以支撑当前最终版架构进入实现阶段。
