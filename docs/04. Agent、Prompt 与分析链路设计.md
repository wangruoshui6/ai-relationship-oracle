## 1. 设计目标

  

本项目的 AI 核心不是简单聊天机器人，而是一个围绕“某个用户与某个对象之间关系”的长期分析链路。

  

目标：

  

1. 判断用户当前问题类型；

2. 支持首次咨询自动提取对象并自动建档；

3. 读取用户与对象的事实档案；

4. 读取关系快照、关系事件、长期摘要和短期上下文；

5. 按用户选择动态调用八字、心理学、塔罗等工具；

6. 检索知识库依据；

7. 融合多体系结构化结果；

8. 生成稳定、温和、可执行的关系建议；

9. 在重大事件触发时更新关系记忆，而不是每轮都写库。

  

---

  

## 2. Agent 模式选择

  

V1 采用：

  

```text

单 Agent + 多 Tool

```

  

不采用：

  

```text

多 Agent 互相对话

```

  

原因：

  

1. V1 重点是上下文质量，不是 Agent 数量；

2. 多 Agent 会显著增加调试复杂度；

3. 输出风格需要统一；

4. 工作流要可追踪、可评测、可回归。

  

---

  

## 3. LangGraph 定位

  

`LangGraph` 在本项目中承担的是：

  

> 工作流编排层

  

它负责：

  

- 管理状态；

- 控制节点执行顺序；

- 根据意图和参数选择路径；

- 加载 Profile 与 Memory；

- 调度工具；

- 管理结果持久化；

- 支撑离线评测系统复用同一条 Agent Workflow。

  

它不是负责排盘，也不是负责最终语言表达本身。

  

---

  

## 4. Prompt 在工作流中的位置

  

用户不会编写 Prompt，Prompt 必须完全由系统内置管理。

  

在本项目中，Prompt 不是只有一段最终系统提示词，而是一个固定模板体系，至少包括三层：

  

1. `全局固定提示词`：定义模型身份、边界、风格、禁令；

2. `节点级提示词`：用于 Router、Extractor、Memory、Event、Compatibility、Report 等内部节点；

3. `场景级提示词`：用于关系分析、情绪支持、通用建议、报告生成等业务场景。

  

其中：

  

- `Prompt Center` = 模板与规则仓库；

- `Prompt Builder` = 运行时拼装器。

  

最终给模型的输入不是用户自己写的提示词，而是：

  

```text

固定提示词

+

动态上下文

=

最终 Prompt

```

  

其中动态上下文包括：

  

- 用户问题

- Facts / Profile

- AI 关系记忆

- `analysis_methods`

- 工具结构化结果

- RAG 依据

## 5. 主流程总览

  

```text

用户输入

  ↓

Intent Router（意图路由器）

  ↓

Entity Extractor（实体提取器）

  ↓

Profile Loader（档案加载器）

  ↓

Memory Loader（记忆加载器）

  ↓

Tool Router（工具路由器）

  ├─ Bazi Engine（八字分析引擎，可选）

  ├─ Psychology Engine（心理学分析引擎，可选）

  └─ Tarot Engine（塔罗分析引擎，可选）

  ↓

Knowledge RAG（知识检索增强生成）

  ↓

Compatibility Engine（融合分析引擎）

  ↓

Prompt Builder（提示词构建器）

  ↓

LLM Generator（大模型生成器）

  ↓

Persist Result（结果持久化）

```

## 7. Prompt Center 最小固定模板体系

  

V1 至少应内置以下固定提示词：

  

### 7.1 全局基础提示词

  

- `system_base_prompt`

  

### 7.2 节点级提示词

  

- `intent_router_prompt`

- `entity_extractor_prompt`

- `psychology_engine_prompt`

- `event_detector_prompt`

- `memory_update_prompt`

- `compatibility_merge_prompt`

- `report_builder_prompt`

  

### 7.3 场景级提示词

  

- `relationship_analysis_prompt`

- `emotional_support_prompt`

- `general_guidance_prompt`

  

这些 Prompt 都是系统预设模板，不由用户输入。

## 8. Intent Router

  

### 8.1 定义

  

负责判断用户当前输入属于什么类型，并决定进入哪条流程。

  

### 8.2 V1 意图分类

  

```text

greeting

emotional_support

relationship_analysis

profile_management

general_guidance

out_of_scope

```

  

### 8.3 处理原则

  

- `greeting`：简短回复，不走完整分析链；

- `emotional_support`：偏情绪支持，可少量读取关系上下文；

- `relationship_analysis`：进入完整主链路；

- `profile_management`：进入档案处理流；

- `general_guidance`：走降级流程；

- `out_of_scope`：礼貌拒绝或边界提示。

  

---

  

## 9. Entity Extractor

  

### 9.1 定义

  

负责从用户输入中抽取：

  

- 关系对象名称，例如 Sarah；

- 可能的关系状态；

- 可能的目标；

- 初始重大事件线索。

  

### 9.2 为什么需要

  

因为首次咨询允许没有 `partner_id`。

  

例如用户直接问：

  

```text

我和 Sarah 分手三个月了，最近她点赞我朋友圈，她会回来吗？

```

  

系统需要先抽取：

  

- `partner = Sarah`

- `status = Breakup`

- `goal = Reconciliation`

- `last_event = LikeMoment`

  

然后自动创建：

  

- `partner_profile`

- `relationship_profile`

- `memory_summary`

  

必要时补一条初始 `relationship_event`。

  

### 9.3 输出示意

  

```json

{

  "partner_name": "Sarah",

  "relationship_status": "Breakup",

  "relationship_goal": "Reconciliation",

  "candidate_events": [

    {

      "event_type": "LIKE_MOMENT",

      "confidence": 0.76

    }

  ]

}

```

  

---

  

## 10. Profile Loader

  

负责读取事实档案：

  

- `user_profile`

- `partner_profile`

  

特点：

  

- 只读取事实层，不读取高层关系语义；

- 读取用户填写和系统计算出的基础命盘信息；

- 如果对象资料不完整，要允许降级。

  

---

  

## 11. Memory Loader

  

负责读取 AI 关系记忆层：

  

- `relationship_profile`

- `relationship_event`

- `memory_summary`

- `conversation_message` 最近片段

- Redis 短期上下文

  

读取优先级：

  

1. `relationship_profile`：当前关系快照；

2. `relationship_event`：历史时间轴；

3. `memory_summary`：长期主摘要；

4. `recent_messages`：短期连续性。

  

说明：

  

- 记忆绑定的是 `user_id + partner_id`，而不是单一 `conversation_id`。

  

---

  

## 12. Tool Router

  

### 12.1 定义

  

根据前端传入的 `analysis_methods` 决定启用哪些工具。

  

### 12.2 前端输入示例

  

```json

{

  "question": "Sarah会回来吗？",

  "analysis_methods": ["bazi", "psychology"]

}

```

  

### 12.3 路由示例

  

如果仅选：

  

- `bazi`

- `psychology`

  

则流程：

  

```text

Relationship Flow

  ↓

Bazi Engine

  ↓

Psychology Engine

  ↓

Compatibility Engine

  ↓

GPT

```

  

如果再加 `tarot`：

  

```text

Relationship Flow

  ↓

Bazi Engine

  ↓

Tarot Engine

  ↓

Psychology Engine

  ↓

Compatibility Engine

  ↓

GPT

```

  

---

  

## 13. Tool Layer 输出规范

  

工具不直接输出面向用户的长文，而是输出结构化结果 JSON。

  

统一结构建议：

  

```json

{

  "tool": "psychology",

  "status": "success",

  "core_signals": [],

  "risks": [],

  "opportunities": [],

  "actions": [],

  "confidence_notes": []

}

```

  

### 13.1 Bazi Engine

  

- 核心排盘与规则计算尽量不用 LLM；

- 可以在解释整理层使用小模型；

- 输出：缘分基础、冲突点、关系节奏、资料缺失说明。

  

### 13.2 Psychology Engine

  

- 可调用小模型分析互动模式；

- 输出：依恋倾向、互动模式、现实风险、沟通建议。

  

### 13.3 Tarot Engine

  

- 抽牌本身不用 LLM；

- 牌义解释可规则化，也可用小模型辅助；

- 输出：牌阵、情感连接、阻碍、趋势、边界说明。

  

### 13.4 RAG

  

- 检索本身不用 LLM；

- 压缩引用摘要可由小模型辅助；

- 输出：相关依据片段与分类标签。

  

---

  

## 14. Compatibility Engine

  

### 14.1 作用

  

把多个工具和关系事实的输出融合成统一中间结果。

  

输入：

  

- `bazi_result`

- `psychology_result`

- `tarot_result`（如启用）

- `relationship_profile`

- `relationship_event`

- `memory_summary`

- `rag_context`

  

输出建议结构：

  

```json

{

  "consensus": [],

  "risks": [],

  "opportunities": [],

  "actions": [],

  "confidence_notes": []

}

```

  

### 14.2 V1 设计建议

  

采用：

  

```text

规则骨架 + LLM 辅助整理

```

  

即：

  

- 先用规则保证字段结构稳定；

- 再允许小模型做轻量语言压缩与归并；

- 最终对用户的表达仍交给主模型。

  

---

  

## 15. Prompt Builder

  

负责把所有结构化上下文组装成最终 Prompt。

  

输入包括：

  

- 固定提示词模板

- 系统角色定义

- 产品边界规则

- 用户问题

- 用户档案

- 对象档案

- 关系快照

- 关系事件时间轴

- 长期记忆摘要

- 短期对话记忆

- 工具结果

- RAG 依据

- Compatibility 结果

  

目标：

  

- 保证输出稳定；

- 避免宿命化；

- 明确边界；

- 强制行动建议优先。

  

---

  

## 16. LLM Generator

  

职责：

  

- 生成用户最终看到的回答；

- 必须遵守 Prompt Center 规则；

- 不直接替代工具层的规则与结构化分析。

  

回答要求：

  

- 有关系判断；

- 有风险提示；

- 有机会点；

- 有行动建议；

- 有资料边界说明；

- 不输出绝对化断言。

  

---

  

## 17. Persist Result

  

### 17.1 每轮必做

  

- 保存 `conversation_message`

  

### 17.2 非每轮都做

  

- 更新 `relationship_profile`

- 新增 `relationship_event`

- 更新 `memory_summary`

  

这些应以事件检测和规则判断为前提。

  

### 17.3 报告生成

  

- 不应每次咨询自动生成 `report`

- 仅在用户主动触发时：

  

```text

用户点击生成报告

  ↓

Report Builder

  ↓

report

```

  

---

  

## 18. Event Detector

  

### 18.1 定义

  

负责从聊天中识别重大关系变化。

  

### 18.2 重大事件示例

  

- 开始恋爱

- 分手

- 断联

- 复联

- 结婚

- 离婚

- 目标改变

  

### 18.3 写入策略

  

- 高置信度：直接写入 `relationship_event`

- 低置信度：进入 `relationship_event_candidate`

- 触发后同步更新 `relationship_profile`

  

### 18.4 为什么不能每轮更新关系快照

  

因为用户大量聊天内容是情绪波动，不等同于关系事实变化。

  

例如：

  

```text

今天有点想她

我还是放不下

其实已经好多了

```

  

这些都不应该直接改写关系主快照。

## 19. 线上与离线统一

  

同一条 `Agent Workflow` 应同时服务：

  

### 线上系统

  

```text

用户 → FastAPI → LangGraph → GPT → 返回结果

```

  

### 离线评测系统

  

```text

Evaluation Harness → Test Cases → Agent Workflow → GPT → Judge → Report

```

  

这样才能保证：

  

- 评测是真实回归测试；

- 线上线下逻辑一致；

- Prompt / Router / Memory / RAG / Compatibility 的改动可量化验证。

## 20. 结论

  

本项目真正的 Agent 主链路可以概括为：

  

```text

用户提问

↓

Router 判断意图

↓

Extractor 自动识别对象并支持首次建档

↓

读取事实档案与 AI 关系记忆

↓

按用户选择调用分析工具

↓

RAG 检索理论依据

↓

Compatibility 统一融合

↓

Prompt Builder 组装固定模板与动态上下文

↓

LLM 生成最终回答

↓

保存聊天，并仅在重大事件时更新关系记忆

```

  

这就是当前最终版架构下最准确的 Agent 运行方式。
