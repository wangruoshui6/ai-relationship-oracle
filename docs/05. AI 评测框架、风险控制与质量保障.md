
## 1. 文档目标

  

本项目不是普通 CRUD 系统，而是一个会持续迭代的 AI 咨询系统。除了接口、数据库和页面测试外，还必须评估：

  

- Prompt 是否变好；

- Router 是否更准；

- Memory 是否更稳；

- Compatibility 是否更完整；

- RAG 是否更相关；

- 最终回答是否更符合产品规则。

  

本文定义：

  

1. `Evaluation Harness` 的定位；

2. `Harness + Ragas` 的 V1 方案；

3. 评测案例与评测库设计；

4. 评分器设计；

5. 安全与风险控制；

6. 回归测试方法。

  

---

  

## 2. 评测体系总架构

  

### 2.1 线上系统

  

```text

用户

  ↓

FastAPI

  ↓

LangGraph

  ↓

GPT / Claude

  ↓

返回结果

```

  

### 2.2 离线评测系统

  

```text

Evaluation Harness

  ↓

测试 Case

  ↓

Agent Workflow

  ↓

GPT / Claude

  ↓

评分器（规则 + LLM Judge + Ragas）

  ↓

评测报告

```

  

关键原则：

  

- 线上系统负责真实用户服务；

- 离线评测系统负责验证改动是否真的让系统变好；

- 两者必须共享同一条 Agent Workflow 主链路。

  

---

  

## 3. 为什么必须要有 Harness

  

因为本项目未来会持续迭代：

  

- `Prompt`

- `Compatibility Engine`

- `Memory Builder`

- `Intent Router`

- `RAG`

  

例如：

  

- 今天是 `Prompt v1.0`

- 明天改成 `Prompt v1.1`

  

如果没有评测系统，就无法知道：

  

- 分析到底变好了还是变差了；

- 哪一类 case 出问题了；

- 是 Prompt 的锅，还是 Router / Memory / RAG 的锅。

  

所以 Harness 本质上是：

  

> 整个 Agent 系统的回归测试平台

  

---

  

## 4. Harness 与 Ragas 的关系

  

V1 不是二选一，而是：

  

```text

Harness 做总控

Ragas 做 RAG 专项评测插件

```

  

推荐结构：

  

```text

Evaluation Harness

 ├── Router Evaluator

 ├── Memory Evaluator

 ├── Compatibility Evaluator

 ├── Final Answer Evaluator

 └── RAG Evaluator（内部接入 Ragas）

```

  

解释：

  

- `Harness` 负责：case 管理、工作流执行、汇总评分、版本对比、评测报告；

- `Ragas` 负责：RAG 检索与 grounding 的专项指标。

  

---

  

## 5. 评测框架定位

  

### 5.1 它是什么

  

它是研发质量保障工具。

  

用于：

  

- 测试 Agent 流程；

- 测试 Prompt 模板；

- 测试记忆更新；

- 测试工具结果注入；

- 测试最终回答；

- 测试安全边界。

  

### 5.2 它不是什么

  

它不是：

  

- 新的 Agent 框架；

- 线上请求中间层；

- 用户可见功能；

- 用来替代业务系统的另一套系统。

## 8. 建议评测什么

  

### 8.1 Intent Router

  

测试输入：

  

- `你好`

- `我失恋了`

- `Sarah 会回来吗`

- `修改我的生日`

  

预期输出：

  

- `Greeting`

- `Emotion`

- `Relationship`

- `Profile`

  

指标：

  

- 路由准确率；

- 混淆矩阵；

- 高风险误分类率。

  

---

  

### 8.2 Memory Builder

  

输入：

  

- 固定 50~100 轮聊天；

- 包含分手、断联、复联、见面等关键事件。

  

验证：

  

- 是否遗漏重大事件；

- 是否把猜测写成事实；

- 是否把不同对象搞混；

- 是否保留关系核心方向。

  

重点规则：

  

- `分手` 不能丢；

- `复联` 不能写错；

- `长期目标` 不能漂移。

  

---

  

### 8.3 Compatibility Engine

  

固定输入示例：

  

```json

{

  "bazi": "有缘分基础",

  "tarot": "有机会重新接触",

  "psychology": "追逃模式风险较高"

}

```

  

验证输出是否稳定包含：

  

- `consensus`

- `risks`

- `opportunities`

- `actions`

  

同时检查：

  

- 是否只说玄学不说现实；

- 是否有风险却没有行动建议；

- 是否自相矛盾。

  

---

  

### 8.4 RAG

  

测试查询：

  

- `夫妻宫`

- `复合`

- `焦虑依恋`

- `断联后恢复联系`

  

验证：

  

- 是否召回正确类别知识；

- 是否出现无关召回；

- 是否有 grounding 问题；

- 是否有效使用检索上下文。

  

这一层由 `RAG Evaluator + Ragas` 共同负责。

  

---

  

### 8.5 最终回答 / 最终报告

  

固定输入：

  

- 用户档案

- 对象档案

- `relationship_profile`

- `relationship_event`

- `memory_summary`

- 用户问题

  

验证：

  

- 是否包含关系分析；

- 是否包含风险；

- 是否包含建议；

- 是否避免绝对化断言；

- 是否符合产品规则；

- 是否结构完整；

- 是否语气稳定。

  

例如：

  

旧版：

  

```text

双方仍存在联系可能

```

  

新版：

  

```text

Sarah 一定会回来

```

  

Harness 应直接判定失败，因为它违反：

  

- 禁止绝对化结论；

- 禁止宿命化表达。

## 10. 评分器设计

  

V1 建议采用三层评分：

  

### 10.1 规则评分

  

适合检查：

  

- 是否缺少某个必须字段；

- 是否出现禁用词；

- 是否输出绝对化表达；

- 是否缺少风险段、建议段。

  

### 10.2 LLM Judge

  

适合检查：

  

- 回答逻辑是否一致；

- 建议是否自然；

- 是否符合温和可信风格；

- 是否合理使用上下文。

  

### 10.3 Ragas

  

适合检查：

  

- retrieval relevance

- context precision / recall

- answer grounding

- faithfulness

## 11. 风险控制重点

  

必须持续监控的高风险问题：

  

1. 绝对化表达；

2. 宿命化断言；

3. 用命理替代现实判断；

4. 健康、法律、金融越界；

5. 把低置信度事件写成事实；

6. 关系对象记忆串线；

7. 工具结果与最终回答矛盾。

  

---

  

## 12. 回归测试原则

  

每次改动以下任一模块，都应该跑评测：

  

- Prompt

- Router

- Memory Builder

- Compatibility Engine

- RAG

- 模型版本

  

回归目标：

  

1. 防退化；

2. 可比较；

3. 可定位问题来源；

4. 可规模化迭代。

  

---

  

## 13. V1 落地建议

  

实施顺序建议：

  

### 第一步

搭 Harness 主框架：

  

- case 读取；

- workflow 执行；

- 结果记录；

- 报告输出。

  

### 第二步

接规则评分 + LLM Judge。

  

### 第三步

把 Ragas 接入 `rag_evaluator`，只负责 RAG 专项指标。

  

---

  

## 14. 结论

  

V1 的正式评测策略应定义为：

  

> 同时建设 `Harness + Ragas`，其中 Harness 负责整条 Agent 工作流的回归测试、版本对比和评测报告，Ragas 负责 RAG 检索与 grounding 的专项评估。

  

这意味着：

  

- 线上系统负责服务用户；

- 关系记忆系统负责沉淀上下文；

- 离线评测系统负责验证每次迭代是否真的更好。
