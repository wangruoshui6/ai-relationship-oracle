## 1. 文档目的

  

本文档定义 `AI Relationship Oracle` V1 的核心接口设计，供前后端联调和后端开发实现参考。

  

本文档已经统一到当前最终架构：

  

- 首次咨询允许无 `partner_id`；

- 系统支持自动对象抽取与自动建档；

- 分析维度由前端传入 `analysis_methods`；

- 关系快照与关系事件主要由系统沉淀；

- 报告由用户主动触发生成；

- 候选事件确认与关系快照人工修正应有独立接口。

  

---

  

## 2. API 设计原则

  

1. REST 风格为主；

2. 资源命名清晰；

3. 咨询链路接口与普通 CRUD 接口分开；

4. 自动建档逻辑在咨询接口内部完成；

5. 返回结构统一；

6. 为候选事件确认、关系纠偏和报告生成留出接口。

  

---

  

## 3. 基础约定

  

### 3.1 Base URL

  

```text

/api/v1

```

  

### 3.2 鉴权方式

  

- `Bearer Token`

  

### 3.3 通用响应结构

  

成功：

  

```json

{

  "code": 0,

  "message": "ok",

  "data": {}

}

```

  

失败：

  

```json

{

  "code": 1001,

  "message": "validation error",

  "data": null

}

```

  

### 3.4 错误码建议

  

```text

0       成功

1001    参数校验失败

1002    未登录或令牌无效

1003    无权限

1004    资源不存在

1005    业务状态不允许

2001    AI 分析失败

2002    外部模型调用失败

2003    工具执行失败

3001    数据库错误

3002    缓存错误

```

## 4. 接口分组总览

  

V1 建议分为：

  

- `auth`

- `profiles`

- `partners`

- `relationship-memory`

- `relationship-event-candidates`

- `conversations`

- `consultations`

- `reports`

- `evaluation`（内部使用）

  

说明：

  

- 旧概念中的 `relationships` 与 `relationship-events` 在 V1 中不再主要作为用户手工维护接口；

- 更准确的做法是：保留系统沉淀后的查询、纠偏、确认能力。

  

---

  

## 5. auth（认证接口）

  

### 5.1 注册

  

```text

POST /api/v1/auth/register

```

  

请求：

  

```json

{

  "email": "user@example.com",

  "password": "12345678"

}

```

  

### 5.2 登录

  

```text

POST /api/v1/auth/login

```

  

请求：

  

```json

{

  "email": "user@example.com",

  "password": "12345678"

}

```

  

### 5.3 当前用户

  

```text

GET /api/v1/auth/me

```

  

---

  

## 6. profiles（本人档案接口）

  

### 6.1 获取我的档案

  

```text

GET /api/v1/profiles/me

```

  

### 6.2 创建或更新我的档案

  

```text

PUT /api/v1/profiles/me

```

  

请求：

  

```json

{

  "gender": "male",

  "birth_date": "1998-05-01",

  "birth_time": "15:30",

  "birth_city": "Beijing",

  "birth_country": "China"

}

```

  

说明：

  

- 保存后后端可同步计算基础命盘并更新 `user_profile`。

  

---

  

## 7. partners（对象档案接口）

  

### 7.1 获取对象列表

  

```text

GET /api/v1/partners

```

  

### 7.2 创建对象

  

```text

POST /api/v1/partners

```

  

请求：

  

```json

{

  "nickname": "Sarah",

  "gender": "female",

  "relationship_type": "ex",

  "birth_date": "1999-03-10",

  "birth_time": "09:00",

  "birth_city": "London",

  "birth_country": "UK"

}

```

  

### 7.3 获取对象详情

  

```text

GET /api/v1/partners/{partner_id}

```

  

### 7.4 更新对象

  

```text

PUT /api/v1/partners/{partner_id}

```

  

### 7.5 删除对象

  

```text

DELETE /api/v1/partners/{partner_id}

```

  

说明：

  

- 对象也可能在首次咨询中由系统自动创建；

- 用户后续可通过这些接口补充或修正对象资料。

## 8. relationship-memory（关系记忆接口）

  

### 8.1 获取某对象的关系记忆详情

  

```text

GET /api/v1/relationship-memory/{partner_id}

```

  

返回示意：

  

```json

{

  "relationship_profile": {

    "current_status": "Breakup",

    "current_goal": "Reconciliation",

    "relationship_stage": "NoContact",

    "last_major_event": "2026-08 Reconnect"

  },

  "relationship_events": [

    {

      "event_type": "BREAKUP",

      "event_date": "2026-05-10",

      "description": "正式分手"

    }

  ],

  "memory_summary": {

    "summary": "用户与 Sarah 恋爱 2 年，2026 年 5 月分手..."

  }

}

```

  

### 8.2 用户修正关系快照

  

```text

PATCH /api/v1/relationship-memory/{partner_id}/profile

```

  

请求示意：

  

```json

{

  "current_status": "Breakup",

  "current_goal": "Reconciliation"

}

```

  

说明：

  

- 这是用户对 AI 自动更新结果的纠偏接口；

- 用户是最终权威。

## 9. relationship-event-candidates（候选事件接口）

  

### 9.1 获取候选事件列表

  

```text

GET /api/v1/relationship-event-candidates?partner_id={partner_id}

```

  

### 9.2 确认候选事件

  

```text

POST /api/v1/relationship-event-candidates/{candidate_id}/confirm

```

  

### 9.3 拒绝候选事件

  

```text

POST /api/v1/relationship-event-candidates/{candidate_id}/reject

```

  

说明：

  

- 低置信度事件不直接进入正式时间轴；

- 需要用户确认后才转入 `relationship_event`。

## 11. consultations（AI 咨询接口）

  

这是最核心接口。

  

### 11.1 发起咨询

  

```text

POST /api/v1/consultations

```

  

请求体示意：

  

```json

{

  "conversation_id": null,

  "partner_id": null,

  "message": "我和 Sarah 分手三个月了，最近她点赞我朋友圈，她会回来吗？",

  "analysis_methods": ["bazi", "psychology"]

}

```

  

说明：

  

- `partner_id` 可以为空；

- 若为空，后端进入：

  

```text

Intent Router

↓

Relationship Flow

↓

Entity Extractor

↓

自动提取 Sarah

↓

自动创建 partner_profile

↓

自动创建 relationship_profile

↓

自动创建 memory_summary

↓

继续分析

```

  

### 11.2 返回体示意

  

```json

{

  "code": 0,

  "message": "ok",

  "data": {

    "conversation_id": "c_001",

    "partner_id": "p_001",

    "auto_created_partner": true,

    "answer": "从当前关系状态来看...",

    "structured_result": {

      "consensus": [],

      "risks": [],

      "opportunities": [],

      "actions": []

    },

    "memory_updated": true,

    "report_generated": false

  }

}

```

  

### 11.3 关键规则

  

- 每轮必须保存 `conversation_message`；

- 不代表每轮都要更新 `relationship_profile`；

- 是否更新关系快照与事件，由 `Event Detector` 和置信度判断决定；

- `analysis_methods` 决定启用哪些工具。

## 12. reports（报告接口）

  

### 12.1 生成报告

  

```text

POST /api/v1/reports

```

  

请求示意：

  

```json

{

  "partner_id": "p_001",

  "report_type": "reconciliation_report",

  "conversation_id": "c_001"

}

```

  

说明：

  

- `report` 不随聊天自动生成；

- 必须由用户主动触发。

  

### 12.2 获取报告列表

  

```text

GET /api/v1/reports

```

  

### 12.3 获取某对象报告列表

  

```text

GET /api/v1/reports?partner_id={partner_id}

```

  

### 12.4 获取报告详情

  

```text

GET /api/v1/reports/{report_id}

```

### 13.2 查看评测结果

## 14. 关键接口设计结论

  

V1 的接口重心不再是：

  

```text

让用户维护完整 relationships / relationship-events CRUD

```

  

而是：

  

```text

让用户输入最少的事实数据

+ 让咨询接口自动建档和自动沉淀记忆

+ 让关系记忆接口支持查看和纠偏

+ 让报告接口独立触发正式输出

```

  

这更符合当前最终版产品架构。
