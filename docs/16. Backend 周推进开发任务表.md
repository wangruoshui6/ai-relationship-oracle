## 1. 文档目标

本文档将当前 `AI Relationship Oracle` 的后端实现任务，拆解为一份按周推进的执行表。

目标不是继续讨论方向，而是给出一份可以直接开工、排期、分配和验收的 backend 任务表。

本文档默认基于以下前提：

- 当前 `backend/` 基本为空，需要从 0 到 1 搭建；
- 以 `FastAPI + SQLAlchemy + Alembic + PostgreSQL + Redis` 为主；
- V1 先保证主闭环，再补增强能力；
- Prompt、LLM Provider、评测体系虽与 AI 侧强相关，但 backend 需要提供承载接口和调用骨架。

---

## 2. 排期假设

建议以 `8 周` 作为 V1 后端主线排期。

适用场景：

- 1 名后端主开发；
- 1 名 AI / Agent 配合；
- 前端并行联调，但本文档只聚焦 backend；
- 每周以“能验收一个闭环”为目标，而不是只完成一批零散模块。

如果人力更少，可以把 8 周拉长到 10~12 周；如果后端和 AI 并行度高，可以压缩到 6 周，但风险会明显上升。

---

## 3. 总体实现顺序

```text
Week 1：工程启动 + 账户与鉴权
Week 2：事实档案层
Week 3：首次咨询最小闭环
Week 4：自动建档与初始关系记忆
Week 5：关系记忆层
Week 6：工具路由与多分析维度
Week 7：报告系统 + 关系纠偏
Week 8：评测接入 + 稳定性收口
```

### 表

```text
register_time
status
created_at
updated_at
```

### 服务

- `ConfigService`
- `DatabaseSessionManager`
- `AuthService`
- `TokenService`

### 具体任务

1. 初始化 FastAPI 项目结构：
   - `app/main.py`
   - `app/api/`
   - `app/core/`
   - `app/db/`
   - `app/models/`
   - `app/schemas/`

   - `app/utils/`

### 验收标准

- Alembic 可生成并执行首个 migration；
- 用户可注册、登录、获取当前身份；
- 未登录请求受保护接口时会返回统一错误结构；
- API 文档可在 OpenAPI 页面正常查看。

### 服务

- `ConversationService`
- `ConsultationService`
- `LLMProviderService`

### 具体任务

1. 建立 `conversation`、`conversation_message` 模型和 migration。
2. 实现会话列表、会话详情接口。
3. 实现 `POST /consultations` 最小流程：
   - 接收 `conversation_id`
   - 接收 `partner_id`
   - 接收 `message`
   - 接收 `analysis_methods`
4. 保存 user message 到 `conversation_message`。

   - user message

- 会话详情能完整回放消息；
- 即使没有 `partner_id`，接口也能先返回一版基础回答；
- 模型调用失败时会返回统一错误码。

   - `greeting`
   - `relationship_analysis`
   - `general_guidance`
   - `out_of_scope`

   - `relationship_status`
   - `relationship_goal`

- 数据库中会自动生成 partner、relationship_profile、memory_summary；
- 同一轮咨询返回结果中能拿到回填后的 `partner_id`；
- 未识别出对象时不会报错，而是优雅降级；
- `memory_summary` 能按 `user_id + partner_id` 唯一维护。

   - `relationship_profile`

- 用户可以确认或拒绝候选事件；
- 用户可人工修正 `relationship_profile`；
- 关系快照不会因普通情绪表达被频繁改写。

## 9. Week 6：工具路由与多分析维度

- Psychology Engine 最小版
- Tarot Engine 占位版
- 统一结果 schema

### 接口

- 继续增强 `POST /api/v1/consultations`

### 表

本周可不新增核心业务表。

如需记录调试数据，可选增加内部日志表，但不是 V1 必需。

### 服务

- `ToolRouterService`
- `BaziEngineService`
- `PsychologyEngineService`
- `TarotEngineService`
- `StructuredResultNormalizer`

### 具体任务

1. 为 `consultations` 接口增加 `analysis_methods` 校验：
   - `bazi`
   - `psychology`
   - `tarot`
2. 实现 Tool Router：
   - 按 methods 决定执行链路
3. 建立统一工具结果结构：
   - `tool`
   - `status`
   - `core_signals`
   - `risks`
   - `opportunities`
   - `actions`
   - `confidence_notes`
4. `Psychology Engine` 先做第一优先级实现。

   - 数据完整时返回基础分析
   - 数据缺失时返回边界提示
6. `Tarot Engine` 先做可选占位版，不阻塞主流程。
7. 在 `consultations` 返回值中增加：
   - `structured_result`
   - `tool_results`

### 验收标准

- 用户可传入不同 `analysis_methods`；
- 系统只运行对应工具；
- 工具结果结构统一；
- 数据不完整时工具能优雅降级；
- 工具不会直接输出面向用户的最终长文。

## 13. 实施时的 8 条硬约束

1. 不能退回到“用户先手工维护完整关系状态”的旧设计。
2. `memory_summary` 必须按 `user_id + partner_id` 唯一维护。
3. `relationship_profile` 不能每轮聊天都更新。
4. 候选事件机制必须保留，不能把所有推断直接写成事实。
5. 工具层只输出结构化结果，不能直接代替最终回答。
6. 聊天与报告必须分离，不能默认自动生成报告。
7. RAG 后续只能做知识依据，不能取代用户关系记忆。
8. Prompt、Router、Memory、Compatibility 的关键改动最终都要能被评测。

---

## 14. 最终里程碑定义

如果 8 周按计划完成，backend 的 V1 应达到以下状态：

1. 用户可注册登录并维护本人与对象档案。
2. 用户可直接发起咨询，即使没有 `partner_id`。
3. 系统可自动识别对象并建立初始关系记忆。
4. 会话和消息可完整保存与回放。
5. 关系快照、关系事件、长期摘要可跨会话复用。
6. 用户可修正关系快照并确认低置信度事件。
7. 后端可按 `analysis_methods` 动态调度工具。
8. 用户可主动生成正式报告。
9. 系统具备最小评测与回归能力。

这时项目就不再是“文档化架构”，而是进入真正可迭代的工程阶段。
