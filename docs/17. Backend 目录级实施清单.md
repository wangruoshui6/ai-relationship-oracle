## 1. 文档目标

本文档把 [16. Backend 周推进开发任务表](/D:/code.agent/agent算命/docs/16.%20Backend%20周推进开发任务表.md) 继续下钻到 `backend/` 目录级别。

## 3. 目录职责约定

### `app/api/`

只放接口层和依赖注入，不承载复杂业务逻辑。

### `app/core/`

放配置、枚举、异常、安全、日志等基础设施代码。

### `app/db/`

放数据库连接、Base、Session 和 repository。

### `app/models/`

只放 ORM 模型定义。

### `app/schemas/`

放 Pydantic 请求体、响应体和内部 DTO。

### `app/services/`

承载业务逻辑，是 backend 主体。

### `app/agents/`

放 workflow、state、node 级封装。即使第一阶段先不用完整 LangGraph，也建议保留目录，避免后面迁移时重构太大。

### `app/tools/`

放多分析维度工具的统一协议和具体实现。

### `app/rag/`

后期放 RAG 相关适配。

### `tests/`

按 `api / services / integration` 分层，不要把所有测试堆到一个目录。

## 13. 文件命名和类命名约定

### 文件命名

- service 文件统一用：`xxx_service.py`
- schema 文件统一用：按领域命名，例如 `consultation.py`
- model 文件统一用：单表单文件，例如 `relationship_profile.py`
- API 文件统一用：复数资源名或语义名

### 类命名

- ORM model：`UserProfile`
- request schema：`UserProfileUpsertRequest`
- response schema：`UserProfileResponse`
- service：`UserProfileService`
- repository：`UserProfileRepository` 或 `ProfileRepo`

建议在这个项目里统一选一种 repository 风格，不要混用。

- `UserStatusEnum`
- `ConversationTypeEnum`

## 14. 两个很重要的实现建议

### 建议 1：先用 service orchestration，后续再平滑接 LangGraph

前 1~4 周，不要让项目被 LangGraph 绑定住。

建议先让：

- `ConsultationService`
- `IntentRouterService`
- `EntityExtractionService`
- `PromptBuilderService`
- `LLMProviderService`

直接串起来跑通主链路。

然后从 Week 4 开始，把这些 service 逐步包进 `agents/nodes/` 和 `workflow.py`。

这样既不会影响实现速度，也能保留后续演进空间。

### 建议 2：schema 要分清“外部接口 schema”和“内部中间结果 schema”

这个项目里会有大量中间结构，例如：

- router result
- entity extraction result
- memory snapshot
- tool result
- report payload

建议把这些也显式写成 schema 或 DTO，不要全用裸 dict，不然后面很快会失控。
