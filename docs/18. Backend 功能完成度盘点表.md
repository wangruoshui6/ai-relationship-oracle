## 1. 文档目标

本文档用于盘点当前 `backend/` 的真实完成状态。

它不再按照最初的 Week 1 ~ Week 8 规划“应该做什么”来判断，而是按当前仓库里**已经存在的代码、路由、migration、测试和手工冒烟结果**来判断：

- 哪些模块已经完成；
- 哪些模块已经接入主链路但仍需收口；
- 哪些模块只是存在文件，还未稳定；
- 哪些模块缺测试、缺联调、缺验收。

本文档的目标是帮助当前阶段做出正确决策：

> 先收口哪些模块，再继续推进哪些能力。

## 10. 当前最推荐的下一步

### 推荐路线

```text
先收口当前主链路
→ 再提交当前阶段
→ 再决定是强化咨询质量，还是强化报告/评测
```

### 最推荐优先检查的 4 个点

1. `consultation_service.py`

原因：

- 它已经是当前整个系统的中心枢纽；
- 依赖最多；
- 任何半成品模块都会从这里暴露问题。

2. `compatibility_engine_service.py`

原因：

- 已进入 consultation 主链路；
- 当前还是新文件；
- 风险高于普通 CRUD。

3. `prompt_center_service.py`

原因：

- 你现在已经不只是单 prompt，而是多 prompt 协同；
- 这一步如果不稳，输出风格会变得不可控。

4. `report_service.py / report_builder_service.py`

原因：

- 已有 integration tests；
- 又在当前工作区中持续修改；
- 很适合现在收口。

## 11. 我对下一步的明确建议

如果只做一件最值的事，我建议：

```text
不要先加新功能。
先做一次“当前 backend 主链路收口”。
```

最务实的执行方式是：

1. 跑完整后端测试。
2. 手工冒烟这几个接口：
   - `POST /auth/token`
   - `POST /consultations`
   - `GET /relationship-memory/{partner_id}`
   - `POST /reports`
   - `POST /evaluation/runs`
3. 看 consultation 是否能稳定走完：
   - Router
   - Extractor
   - Auto-create partner
   - Bootstrap memory
   - Tool router
   - Compatibility
   - LLM output
4. 只要这条线稳定，再提交当前阶段。
