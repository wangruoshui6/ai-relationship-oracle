## 1. 文档目标

本文档定义 `AI Relationship Oracle` 中“资料分析页”的前后端接口与字段设计。

这个页面的目标不是替代当前的“快速咨询页”，而是提供一个更适合：

- 八字排盘
- 合盘
- 正式分析
- 农历 / 公历资料输入
- 报告生成前置资料补全

的结构化入口。

本文档会明确：

- 页面结构
- 字段定义
- 公历 / 农历处理方式
- 前后端交互流程
- 后端接口设计
- 程序应该如何继续走 consultation / report 链路

---

## 2. 为什么要单独做“资料分析页”

当前项目实际上有两种不同的用户进入方式：

### 2.1 快速咨询页

适合：

- 先问问题
- 不想先填太多资料
- 允许系统自动识别对象

特点：

- 低门槛
- 快进入
- 更偏情感咨询

### 2.2 资料分析页

适合：

- 明确想做八字 / 合盘 / 多维分析
- 愿意先填资料
- 需要支持农历输入
- 需要更稳定的结构化结果

特点：

- 资料完整
- 八字计算更准
- 更适合正式分析与报告

---

## 3. 产品定位

资料分析页本质上应定义为：

```text
结构化资料录入 + 八字计算前置 + 正式分析入口
```

而不是：

```text
普通聊天页的另一个皮肤
```

它的核心职责是：

1. 采集用户本人资料；
2. 采集对象资料；
3. 支持公历 / 农历切换；
4. 在进入咨询前完成日期归一化和八字计算；
5. 将资料写入 `user_profile` / `partner_profile`；
6. 再进入 consultation / report 主链路。

---

## 4. 页面结构设计

建议页面结构分为 5 个区域：

### A. 分析模式区

用于定义这次分析是：

- 新分析
- 基于已有对象继续分析

建议控件：

- `选择已有对象`
- `新建对象并分析`

### B. 我的资料区

字段：

- 性别
- 公历 / 农历
- 出生日期
- 是否闰月（仅农历显示）
- 出生时间
- 出生地点

### C. 对方资料区

字段：

- 昵称
- 性别
- 关系类型
- 公历 / 农历
- 出生日期
- 是否闰月（仅农历显示）
- 出生时间
- 出生地点

### D. 分析设置区

字段：

- 分析维度
  - `bazi`
  - `psychology`
  - `tarot`
- 分析类型
  - 感情现状
  - 复合可能
  - 长期适配
  - 正式报告

### E. 提问区

字段：

- 自由问题输入框

示例：

```text
我们现在处于分开状态，之前分分合合，我想知道还有没有复合可能。
```

## 5. 前端字段定义

### 5.1 通用日期输入字段

```ts
type CalendarType = "solar" | "lunar";
```

```ts
type BirthInput = {
  calendar_type: CalendarType;
  birth_date: string | null;      // YYYY-MM-DD
  is_leap_month: boolean;
  birth_time: string | null;      // HH:mm:ss
  birth_city: string | null;
  birth_country: string | null;
};
```

说明：

- `birth_date` 前端统一用字符串 `YYYY-MM-DD`
- 如果是农历：
  - `birth_date` 表示用户输入的农历日期
  - 后端负责转公历
- `is_leap_month` 只有在农历模式下有意义

### 5.2 我的资料字段

```ts
type UserProfileDraft = {
  gender: "male" | "female" | "other" | "unknown" | null;
} & BirthInput;
```

### 5.3 对方资料字段

```ts
type PartnerProfileDraft = {
  nickname: string;
  gender: "male" | "female" | "other" | "unknown" | null;
  relationship_type: "ex" | "current" | "crush" | "spouse" | "friend" | "unknown" | null;
} & BirthInput;
```

### 5.4 分析设置字段

```ts
type AnalysisDraft = {
  analysis_methods: Array<"bazi" | "psychology" | "tarot">;
  question: string;
  report_type?: string | null;
};
```

## 6. 前端交互流程

### 路径 1：新建对象并分析

```text
填写我的资料
↓
填写对方资料
↓
点击“保存并开始分析”
↓
后端：
1. 归一化日期
2. 计算八字
3. 保存 user_profile / partner_profile
4. 发起 consultation
↓
返回分析结果
```

### 路径 2：已有对象继续分析

```text
选择已有对象
↓
页面自动带出对象资料
↓
如有需要补充修改
↓
发起 consultation
```

## 7. 推荐的前后端分层

### 前端职责

- 展示公历 / 农历选择器
- 控制字段显示逻辑
- 采集原始输入
- 不负责自己计算八字
- 不负责自己转换农历

### 后端职责

- 校验资料
- 农历转公历
- 保存原始农历日期
- 计算八字盘
- 落库
- 再进入 consultation / report

这条分工非常重要：

```text
算盘由 Python 规则层负责
解盘由 LLM 负责
```

## 8. 建议的后端接口设计

我建议不要把“资料分析页”直接硬塞进现有 `PUT /profiles/me + POST /partners + POST /consultations` 三次调用里。

虽然三次调用也能工作，但从页面体验和状态一致性看，**更适合新增一个聚合接口**。

---

## 9. 新增接口建议

### 9.1 资料分析预处理接口

```text
POST /api/v1/analysis-intake
```

作用：

- 同时接收用户资料 + 对方资料 + 分析问题
- 做日期归一化
- 做八字计算
- 落库
- 返回生成后的 profile / partner 基础结果

### 请求体

```json
{
  "user_profile": {
    "gender": "male",
    "calendar_type": "solar",
    "birth_date": "2005-08-25",
    "is_leap_month": false,
    "birth_time": "10:20:00",
    "birth_city": "Tangshan",
    "birth_country": "China"
  },
  "partner_profile": {
    "nickname": "她",
    "gender": "female",
    "relationship_type": "unknown",
    "calendar_type": "lunar",
    "birth_date": "2007-01-27",
    "is_leap_month": false,
    "birth_time": "02:05:00",
    "birth_city": "Shijiazhuang",
    "birth_country": "China"
  },
  "question": "我们现在分开了，还能复合吗？",
  "analysis_methods": ["bazi", "psychology"]
}
```

### 返回体建议

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "user_profile_saved": true,
    "partner_profile_saved": true,
    "partner_id": "p_001",
    "normalized_dates": {
      "user_birth_date": "2005-08-25",
      "user_lunar_birth_date": null,
      "partner_birth_date": "2007-03-16",
      "partner_lunar_birth_date": "2007-01-27"
    },
    "bazi_ready": {
      "user": true,
      "partner": true
    }
  }
}
```

### 9.2 资料分析一键咨询接口

另一种更强的方式，是直接让它一口气：

- intake
- normalize
- bazi compute
- persist

## 10. 我更推荐哪种接口

### 推荐：`structured-consultations`

原因：

- 页面点击一次即可完成完整流程
- 更贴合“资料分析页”这个产品形态
- 避免前端自己串三四个接口
- 状态一致性更好

### 可选保留：`analysis-intake`

适合：

- 你后面想做“先保存资料，再稍后分析”
- 或想做“资料检查页”

---

## 11. 后端内部处理流程建议

`structured-consultations` 的内部逻辑建议是：

```text
1. 校验 user_profile / partner_profile 输入
2. 归一化日期
3. 更新 user_profile
4. 创建或更新 partner_profile
5. 计算双方八字
6. 进入 consultation 主链路
7. 返回 answer + structured_result
```

### 其中关键步骤

#### 日期归一化

- 如果 `calendar_type = solar`
  - `birth_date` 直接进入 profile
- 如果 `calendar_type = lunar`
  - `birth_date` 保存到 `lunar_birth_date`
  - 转换后公历日期写入 `birth_date`

#### 八字计算

- 统一用归一化后的公历日期计算
- 不让 LLM 猜命盘

## 13. 资料分析页与快速咨询页的关系

建议明确成：

### 快速咨询页

- 适合“先问问题”
- 不强制先填对象完整资料
- 自动识别对象

### 资料分析页

- 适合“想认真做八字/合盘”
- 强调结构化录入
- 更适合正式分析与报告

这两页不是互相替代，而是：

```text
低门槛入口
+
高质量分析入口
```

## 16. 结论

“资料分析页”的正确结构应该是：

```text
用户填写结构化出生资料
↓
后端做公历/农历归一化
↓
Python 计算八字
↓
保存 profile
↓
进入 consultation / report
```

这比“让 LLM 从一大段自然语言里自动猜两个人的出生资料和历法”更稳定，也更符合当前项目阶段。
